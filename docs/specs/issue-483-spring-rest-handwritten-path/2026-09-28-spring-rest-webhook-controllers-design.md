# Design: Spring REST controllers for hand-written @Path resources

**Issue:** casehubio/parent#483
**Date:** 2026-09-28
**Branch:** issue-483-spring-rest-handwritten-path
**Revision:** R2 (post design-review)

## Problem

Platform has hand-written `@Path` JAX-RS resources that need Spring REST equivalents.
Of the 6 resources originally identified, 3 are already generated via `@McpDomain`
(PreferenceSchemaResource, SubscriptionService, EventTypeService). The remaining 3 need work:

| Resource | Module | Pattern | Has -core POJO? |
|----------|--------|---------|-----------------|
| CallbackDispatchResource | callback-client | @McpDomain + @PlatformWebhook | Yes (callback-client-core) |
| EngagementCallbackResource | notification-dispatch | @McpDomain + @PlatformWebhook + @PlatformMutation | Yes (notification-dispatch-core) |
| WebhookResource | streams-webhook | Raw @Path (no @McpDomain) | Yes (streams-webhook-core) |

All three are webhook-style POST endpoints with bearer token auth and HttpHeaders
injection. All have -core POJOs with constructor injection — the Quarkus resources
are thin delegates.

**Critical constraint:** `@McpDomain` currently lives on the Quarkus resource classes
(CallbackDispatchResource, EngagementCallbackResource), NOT on the -core POJOs. The
generator scans `@McpDomain` classes and delegates to them — if it scans the Quarkus
resource, the generated Spring controller wraps JAX-RS `Response` objects in
`ResponseEntity`, which is semantically wrong. `@McpDomain` must be moved to the -core
classes for all 3 resources.

## Solution

Three-layer approach: extend the shared scanner to support `@PlatformWebhook` (porting
from the APT reference implementation), extend the Spring writer to generate webhook
controllers, then wire up the target modules.

### Prerequisite: Move @McpDomain to -core classes

For callback-client and notification-dispatch, move `@McpDomain`, `@PlatformWebhook`,
`@PlatformMutation`, `@PathParam`, and `@HeaderParam` annotations from the Quarkus
resource classes to the -core POJOs. The -core methods already return POJOs
(`DispatchResult`, `void`), not JAX-RS `Response` — the generator can handle these
directly.

The Quarkus resources remain as thin wrappers (generated by the APT from the -core
`@McpDomain`), but the generator's `sourceFqcn()` now points to the -core class.

### Layer 1: generator-common — shared scanner extension

Port the APT's existing WEBHOOK support to `McpDomainJandexScanner`. The APT
(`GraphQLResolverProcessor`) is the reference implementation — field names and types
must match exactly.

1. **Add `WEBHOOK` to `OperationType` enum** — currently QUERY/MUTATION/STREAM
2. **Scan `@PlatformWebhook` annotation** — extract:
   - `consumes` — `String[]` (default `{"application/json"}`), NOT `String`
   - `@PermitAll` — derived from `@jakarta.annotation.security.PermitAll` on the
     method (NOT a field on `@PlatformWebhook` — the annotation has no `permitAll`
     attribute)
   - Passed annotations — collected from the method's own annotations
3. **Extend `ResolvedParam`** with:
   - `isHeaderParam` + `headerParamName` — for `@HeaderParam` parameters
   - `isQueryParam` + `queryParamName` — for `@QueryParam` parameters
   (Port from APT's `ResolvedParam` lines 1938–1955)
4. **Extend `ResolvedOperation`** with:
   - `webhookConsumes` — `String[]` (matching APT field type)
   - `permitAll` — boolean (derived from method-level `@PermitAll`)
   - `passedAnnotations` — list of annotation class names to propagate

### Layer 2: graphql-spring-generator — Spring writer extension

#### 2a. SpringDomainRestControllerWriter — webhook method generation

Add `buildWebhookMethod()`:

```java
@PostMapping(path = "/<path>", consumes = {"application/cloudevents+json"})
@PermitAll  // when permitAll=true on ResolvedOperation
public ResponseEntity<?> methodName(
    @PathParam String tenancyId,          // from @PathParam on -core method
    @PathParam String streamId,           // from @PathParam on -core method
    @RequestHeader HttpHeaders headers,   // from @HeaderParam or passthrough
    @RequestBody byte[] body) {           // preserve original body type
    WebhookResult result = delegate.receive(body, tenancyId, streamId, headersMap);
    return ResponseEntity.status(result.status()).body(result.body());
}
```

Key differences from `buildRestMethod()`:
- Always POST (no HTTP verb inference)
- `@PermitAll` from method annotation, not `@RolesAllowed`
- Consumes from `@PlatformWebhook.consumes()` (`String[]`)
- Preserve return type semantics (WebhookResult → status code mapping)

#### 2b. @HeaderParam → @RequestHeader generation

Add header param detection to the parameter generation loop. When `ResolvedParam`
has `isHeaderParam=true`:
- Generate `@RequestHeader("<headerParamName>") Type paramName` on the Spring method
- Pass through to delegate call directly

This handles `@HeaderParam("X-CaseHub-SPI")` on CallbackDispatchResource and any
future header params.

#### 2c. httpHeaders passthrough (NOT contextParamResolution)

`contextParamResolution()` returns code expressions from fields (e.g.,
`currentPrincipal.tenancyId()`). HttpHeaders cannot use this mechanism — headers
must come from a **method parameter**, not a field.

Instead, when a -core method parameter is typed as `Map<String, String>` (headers)
or the `@ContextParam("httpHeaders")` annotation is present:
- Add `@RequestHeader HttpHeaders headers` to the generated method signature
- Convert `HttpHeaders` → `Map<String, String>` before calling the delegate:
  `headers.toSingleValueMap()`

#### 2d. SpringGraphqlControllerWriter — WEBHOOK filtering

Adding `WEBHOOK` to `OperationType` breaks the exhaustive switch in
`SpringGraphqlControllerWriter.buildMethod()`:
```java
case QUERY -> QUERY_MAPPING;
case MUTATION -> MUTATION_MAPPING;
case STREAM -> SUBSCRIPTION_MAPPING;
// WEBHOOK has no GraphQL mapping
```

Fix: filter out WEBHOOK operations before they reach `buildMethod()`. Webhooks
are REST-only by definition — they have no GraphQL equivalent.

#### 2e. Security annotation mapping

- `@PermitAll` on webhook methods → generate `@PermitAll` (Jakarta annotation,
  matching APT behavior and existing Spring writer convention which uses
  `@RolesAllowed`, not `@PreAuthorize`)
- Non-PermitAll methods → existing `@RolesAllowed` logic unchanged

### Layer 3: Module wiring

#### 3a. Move @McpDomain to -core classes (all 3 resources)

**callback-client-core:** Move `@McpDomain("casehub/callbacks")`, `@PlatformWebhook`,
and `@HeaderParam` from `CallbackDispatchResource` to `CallbackDispatcher`. The
Quarkus resource becomes generated.

**notification-dispatch-core:** Move `@McpDomain("delivery/engagement")`,
`@PlatformWebhook`, and `@PlatformMutation` from `EngagementCallbackResource` to
`EngagementCallbackService`.

**streams-webhook-core:** Add `@McpDomain("streams/webhook")` and
`@PlatformWebhook(consumes = {"application/cloudevents+json"})` to `WebhookReceiver`.
Preserve existing method signatures:
- Return type: `WebhookResult` (carries HTTP status codes — 202/400/401/404)
- Body type: `byte[]` (CloudEvents require binary deserialization)
- tenancyId: `@PathParam` (URL path segment, NOT `@ContextParam` — external systems
  specify the target tenant in the URL, not via authentication)
- headers: `Map<String, String>` (current type, not Spring `HttpHeaders`)

The existing hand-written `WebhookResource` in streams-webhook is replaced by the
graphql-generator APT output.

#### 3b. callback-spring — add graphql-spring-generator

Add `graphql-spring-generator` Maven plugin to callback-spring POM:
- `<quarkusModule>callback-client-core</quarkusModule>`
- Generates `CallbackDispatchController` from `@McpDomain("casehub/callbacks")`
  on CallbackDispatcher

#### 3c. notification-dispatch-spring — new module

Create `notification-dispatch-spring` with graphql-spring-generator:
- `<quarkusModule>notification-dispatch-core</quarkusModule>`
- Generates `EngagementCallbackController` from `@McpDomain("delivery/engagement")`
  on EngagementCallbackService
- Auto-configuration class for `EngagementCallbackService` bean (5 constructor deps:
  `DeliveryAttemptStore`, `EngagementRecorder`, `CurrentPrincipal`,
  `Map<String, EngagementCallbackHandler>`, `PreferenceProvider`)
- The `Map<String, EngagementCallbackHandler>` requires a `@Bean` method collecting
  handlers by channel ID — cannot use simple auto-wiring
- Parent POM: add `<module>notification-dispatch-spring</module>`
- Include in `spring-boot-starter` dependencies

#### 3d. streams-spring — webhook controller

`streams-spring` already consolidates all stream adapter auto-configs (Kafka,
AMQP, Camel, Poll). Add graphql-spring-generator:
- `<quarkusModule>streams-webhook-core</quarkusModule>`
- Generates `WebhookController` from `@McpDomain("streams/webhook")` on
  WebhookReceiver

## Testing

- **Generator unit tests:** extend existing `graphql-spring-generator` tests with
  a @PlatformWebhook test fixture — verify generated controller has @PostMapping
  with String[] consumes, @RequestBody with original type, @RequestHeader for
  header params, @PermitAll when present
- **Scanner tests:** extend `McpDomainJandexScanner` tests to verify WEBHOOK
  operations are discovered with correct metadata (String[] consumes, permitAll
  from method annotation, headerParam/queryParam on ResolvedParam)
- **GraphQL writer test:** verify WEBHOOK operations are filtered out (no
  exhaustive switch failure)
- **spring-integration-test:** verify generated webhook controllers compose in the
  Spring Boot context (ApplicationContext loads, beans wired)
- **Verify goals:** each module's `verify` Mojo confirms generated output matches
  expectations (drift detection)

## Out of scope

- GraphQL mapping for webhook endpoints (webhooks are REST-only by nature —
  WEBHOOK operations filtered from GraphQL writer)
- WebSocket/SSE — handled by existing Stream support
- Quarkus-side changes beyond @McpDomain relocation — the APT already handles
  WEBHOOK for all other resources; moving @McpDomain to -core is additive
