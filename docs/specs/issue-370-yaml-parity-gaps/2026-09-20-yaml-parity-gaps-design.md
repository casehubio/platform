# YAML Parity Gaps — Design Spec

**Issue:** casehubio/platform#370
**Branch:** issue-370-yaml-parity-gaps
**Date:** 2026-09-20
**Depends on:** simulation-config-core, simulation-generator (existing modules)

---

## Context

Issue #370 identified four YAML parity gaps. Three are now closed by the
#352 simulation DX work (exhaustion policy, threshold, and corpus loading
are all YAML-declarable via `YamlSimulationConfig`). Two narrower gaps
remain:

1. **Parameter-name key extraction** — bare parameter names as
   `key-extractor` specs, resolved via APT-emitted metadata
2. **Format-independent corpus loading** — a `CorpusLoader` SPI with
   YAML and CSV implementations, extracting the private logic from
   `YamlSimulationConfig` into reusable public classes

## Deliverable 1: Parameter-name key extraction

### 1.1 APT parameter registry

`SimulationDecoratorProcessor` already has parameter names at build time
via `method.parameterName(i)`. It will emit an additional classpath
resource alongside each decorator:

**File:** `META-INF/simulation-parameters.properties`

```properties
# Generated by SimulationDecoratorProcessor — do not edit
bank-feed-platform.balance=accountId:0
bank-feed-platform.listAccounts=
bank-feed-platform.getTransaction=transactionId:0
bank-feed-platform.transfer=fromAccount:0,toAccount:1,amount:2
```

Format: `qualifiedName=paramName:position[,paramName:position]*`

Empty value = zero-arg method (no parameters to extract from).
Multiple JARs contribute entries — the runtime loads all files from
the classpath via `ClassLoader.getResources()`.

### 1.2 ParameterRegistry

New class in `simulation-config-core`:

```java
public class ParameterRegistry {

    private final Map<String, MethodParams> methods;

    public static ParameterRegistry loadFromClasspath() {
        // Load all META-INF/simulation-parameters.properties from classpath
        // Parse into MethodParams records
    }

    public Optional<MethodParams> paramsFor(String qualifiedName) {
        return Optional.ofNullable(methods.get(qualifiedName));
    }

    public record MethodParams(Map<String, Integer> nameToPosition, int totalParams) {
        public Optional<Integer> positionOf(String paramName) {
            return Optional.ofNullable(nameToPosition.get(paramName));
        }
    }
}
```

### 1.3 DeclarativeExtractorFactory changes

The factory gains a `ParameterRegistry` constructor parameter. The
`create()` method gains a `qualifiedName` parameter (the method QN)
alongside the existing `spec` parameter. Resolution order:

1. `identity` → `String::valueOf`
2. `field:*` → Jackson field extraction from Map
3. `composite:*` → multi-field concatenation
4. `rest-client` → RestInvocation path extraction
5. **New: bare parameter name** → consult `ParameterRegistry`:
   - Name found, `totalParams == 1` → identity (`String::valueOf`)
   - Name found, `totalParams > 1` → `((Object[])input)[position].toString()`
   - Name not found → throw with helpful message listing valid names
6. Unknown spec → throw (existing behavior)

```java
public KeyExtractor<Object> create(String spec, String qualifiedName) {
    // Steps 1-4: existing prefix dispatch (unchanged)
    // Step 5: bare parameter name
    if (parameterRegistry != null) {
        var params = parameterRegistry.paramsFor(qualifiedName);
        if (params.isPresent()) {
            var pos = params.get().positionOf(spec);
            if (pos.isPresent()) {
                int index = pos.get();
                if (params.get().totalParams() == 1) {
                    return input -> String.valueOf(input);
                }
                return input -> String.valueOf(((Object[]) input)[index]);
            }
            throw new SimulationConfigException(
                "Unknown key-extractor spec: '" + spec + "' for " + qualifiedName
                + ". Known parameters: " + params.get().nameToPosition().keySet()
                + ". Valid specs: identity, field:<name>, composite:<f1>,<f2>, "
                + "rest-client, or a parameter name.");
        }
    }
    // Step 6: unknown
    throw new SimulationConfigException("Unknown key-extractor spec: " + spec + "...");
}
```

The old `create(String spec)` method is retained for backward compatibility
— it delegates to `create(spec, null)` which skips the registry lookup.

## Deliverable 2: Format-independent corpus loading

### 2.1 CorpusLoader SPI

New interface in `simulation-config-core`:

```java
public interface CorpusLoader {

    boolean supports(String path);

    Map<String, List<InvocationRecord<Object, Object>>> load(
            InputStream input, String defaultTenancyId);
}
```

`supports()` checks file extension. `load()` parses the stream and
returns corpus entries keyed by qualified name.

### 2.3 CsvCorpusLoader

New implementation for CSV corpus files. CSV is a natural format for
industries with tabular reference data (finance, clinical, regulatory).

**CSV format convention:**

```csv
_qualified_name,_key,_tenancy_id,accountId,name,balance
bank-feed-platform.balance,acct-123,tenant-a,acct-123,Checking,1234.56
bank-feed-platform.balance,acct-456,tenant-a,acct-456,Savings,5678.90
```

Column conventions:
- `_qualified_name` — **required** column, maps the row to a simulation method
- `_key` — optional, the corpus entry key (for key-lookup strategy)
- `_tenancy_id` — optional, falls back to `defaultTenancyId`
- All other columns → the output `Map<String, Object>` (values parsed
  as String by default; numeric/boolean detection via simple heuristic)

The input is derived from the key column value (for key-lookup) or null
(for sequential). This matches the common CSV use case: tabular reference
data where the lookup key is one column and the response is the full row.

```java
public class CsvCorpusLoader implements CorpusLoader {

    @Override
    public boolean supports(String path) {
        return path.toLowerCase().endsWith(".csv");
    }

    @Override
    public Map<String, List<InvocationRecord<Object, Object>>> load(
            InputStream input, String defaultTenancyId) {
        // Read CSV with first-row header
        // Group rows by _qualified_name
        // For each row: key = _key column, tenancyId = _tenancy_id column,
        //   input = key value (or null), output = Map of remaining columns
    }
}
```

**JSON support:** JSON corpus files use the same structure as YAML (qualified
name → list of entries). `YamlCorpusLoader` handles `.yaml`/`.yml` only
(uses `ObjectMapper(YAMLFactory)`). A thin `JsonCorpusLoader` handles `.json`
using `new ObjectMapper()` (no YAMLFactory — `YAMLFactory` cannot parse JSON).
Both share the same entry-to-InvocationRecord conversion logic via a
shared `CorpusEntryParser` utility method.

### 2.4 CompositeCorpusLoader

Aggregates registered loaders and dispatches by extension:

```java
public class CompositeCorpusLoader implements CorpusLoader {

    private final List<CorpusLoader> loaders;

    public CompositeCorpusLoader(CorpusLoader... loaders) {
        this.loaders = List.of(loaders);
    }

    @Override
    public boolean supports(String path) {
        return loaders.stream().anyMatch(l -> l.supports(path));
    }

    @Override
    public Map<String, List<InvocationRecord<Object, Object>>> load(
            InputStream input, String defaultTenancyId) {
        throw new UnsupportedOperationException(
            "Use loadPath() — CompositeCorpusLoader dispatches by path");
    }

    public Map<String, List<InvocationRecord<Object, Object>>> loadFromPaths(
            List<String> paths, String defaultTenancyId) {
        Map<String, List<InvocationRecord<Object, Object>>> merged = new HashMap<>();
        for (String path : paths) {
            CorpusLoader loader = loaders.stream()
                .filter(l -> l.supports(path))
                .findFirst()
                .orElseThrow(() -> new SimulationConfigException(
                    "No corpus loader for: " + path
                    + ". Supported extensions: .yaml, .yml, .json, .csv"));
            try (InputStream is = openStream(path.trim())) {
                loader.load(is, defaultTenancyId)
                    .forEach((qn, records) ->
                        merged.computeIfAbsent(qn, k -> new ArrayList<>())
                            .addAll(records));
            }
        }
        return merged;
    }
}
```

### 2.5 YamlSimulationConfig refactor

`YamlSimulationConfig.loadExternalCorpusFiles()` delegates to
`CompositeCorpusLoader.loadFromPaths()`. The `openStream()` method moves
to a shared utility (or to `CompositeCorpusLoader`).

## Module placement

All changes are in existing modules — no new modules:

| Module | Changes |
|--------|---------|
| `simulation-generator` | APT emits `META-INF/simulation-parameters.properties` |
| `simulation-config-core` | `ParameterRegistry`, `CorpusLoader` SPI, `YamlCorpusLoader`, `CsvCorpusLoader`, `CompositeCorpusLoader`, `DeclarativeExtractorFactory` changes |
| `simulation-config` | `SimulationConfigBeans` wiring updates |

No new dependencies. CSV parsing uses `BufferedReader` + `String.split()`
(no external CSV library). Jackson is already a compile dependency.

## What this does NOT do

- **Type-aware CSV parsing** — CSV values are String by default with
  simple numeric/boolean heuristics. No schema-driven type coercion.
- **Nested field paths in extractors** — `field:address.city` not
  supported. Use programmatic extractors for nested access.
- **Runtime parameter registry updates** — registry is loaded once at
  startup from classpath resources.
- **CSV with quoted commas** — the parser handles simple CSVs. For
  complex CSV (RFC 4180 with quoted fields), use YAML or JSON instead.
